GRPO proof-of-life on Qwen3.6-27B

Faisal · July 16, 2026 · the plan we execute the moment Michael sends the model API key + SSH. Every benchmark fact below was verified against source code and papers over July 15–16.

This is the dress rehearsal before we point RL at our own environment. It answers one question — can we take Qwen3.6-27B and, with GRPO, move a program-scored slide benchmark by +2–3% on a measurement that can't be faked? If yes, the training plumbing, reward mapping, and honest-measurement method are all proven, and Phase 2 (powerbench) starts on July 28 with the risky parts already de-risked.

1.  What this proves — and what it does not

GRPO (Group Relative Policy Optimization) is our training method: the model attempts each task several times, a grader scores every attempt, and the model is nudged toward whatever scored higher. This experiment proves three things end-to-end:

  • the training loop runs on the 27B without exploding (config, memory, throughput);
  • a grader's numbers can be turned into a learning signal (the reward mapping) that actually raises the score;
  • we can measure the gain on a contamination-proof held-out set — i.e., the improvement is real, not memorized.

It deliberately does not prove template-conformance or the multi-turn agent loop — those are powerbench's job. SlidesBench is single-shot slide-code generation, so it isolates the plumbing cleanly. Treat a pass here as "the machine works," not "the product works."

2.  Hypotheses (stated so they can fail)

H1 — trainable zone. At baseline, Qwen3.6-27B scores in a workable middle band on SlidesBench's reference-based metrics — high enough to have signal, low enough to have headroom. Fails if it already scores near the ceiling (nothing to learn) or near zero (no gradient to climb).
H2 — the gain is real. After GRPO, the 27B improves by ≥ +2–3% on the perturbed held-out set (defined in §5), not just the official one. Fails if gains appear only on the official set (= memorization) or nowhere.
H3 — eval sanity. The 27B's baseline lands sensibly against SlidesBench's published leaderboard (GPT-4o, the paper's own trained model) — not absurdly high, not on the floor. This confirms our scoring pipeline is wired correctly before we trust any training delta. It costs nothing — a comparison to numbers already in the paper, not a second model we have to run.

One model, on purpose. A proof-of-life needs exactly the model we intend to train — nothing else. We are not running a big second model as a yardstick: it would be too large and expensive to be worth it here, and we don't need one to prove the loop works. Input mode: SlidesBench ships three instruction variants — with-image, high-level, and no-image. We run the 27B on the with-image variant: it's vision-capable, and this mirrors how the real pptx skill's render→look→fix loop actually works. We'll also record the no_image score as a harder reference point.

4.  Benchmark & metrics — what we score, what we throw out

Target: SlidesBench (from the AutoPresent paper). The model writes Python that builds a .pptx; we execute it and score the result. Verified by reading evaluate/page_eval.py directly — these four metrics are deterministic .pptx-vs-.pptx comparisons with no AI in the loop:

MetricWhat it checksUse?
Execution successDid the generated code run and produce a valid pptx?Yes — reward gate
Text similarityDoes the slide text match the reference?Yes
Color similarity (CIEDE2000)Are colors within perceptual distance of the reference?Yes
Position similarityAre elements placed where the reference has them?Yes
Element / block matchAre the right elements present (max-matching)?Yes
Reference-free "design quality"Overall aesthetic judgmentNo — GPT-4o-judged, not deterministic
CLIP image-similarityVisual embedding matchNo — model-based, hackable

We score on the reference-based deterministic family only. Dropping the two model-based metrics is what keeps the reward un-gameable and the +2–3% a fact rather than an opinion.

5.  Contamination controls — the honest-measurement method

SlidesBench has been public since January 2025, ~15 months before the 27B's April 2026 release, and Alibaba publishes no data cutoff — so the model may have seen the test answers. We neutralize this two ways. (Reminder: contamination only poisons the measurement; training on seen data is fine — it's what fine-tuning is.)

5a. Memorization probe (~30 min, run first)

Feed each model half of a test instruction and see if it completes the reference verbatim; and check whether baseline scores sit implausibly above the published state of the art. Either signal ⇒ the official test set is contaminated and we lean entirely on the perturbed set below.

5b. Perturbed held-out set (the real eval, ~½ day to build)

Take ~50 test tasks and programmatically alter each reference slide, then regenerate the instruction from the altered slide so the task stays self-consistent. Memorized answers are now wrong by construction. Operators:

  • Color — shift each themed color by a controlled perceptual distance (swap palette entry / rotate hue).
  • Text — replace titles/body with novel strings, same structure.
  • Position — translate element bounding boxes.
  • Element count — add or drop a required element.

Close the loop with SlidesBench's own create_dataset.py / seed_instruction.py — perturb the reference, regenerate its instruction, re-score. This is also how we'll mint our own training tasks (the official 7k download is broken; unofficial mirrors are unknown fidelity). Pre-check: confirm the deterministic metrics don't produce degenerate scores under our operators before trusting the numbers — the one open question the verification pass flagged. Report official and perturbed scores side by side; if they diverge, the perturbed number is the truth.

6.  Training setup

  • Framework: verl (GRPO is first-class; the Qwen3-MoE family is its worked example). Method: LoRA-GRPO — train small add-on layers, not all 27B weights, so it fits the box and the window.
  • Group size: 8 rollouts per prompt to start (matches our k=8 convention and AeSlides' setup), advantage = reward minus group mean.
  • Starting knobs to tune in Gate 1: LoRA rank ~32, one epoch over the minted train set, response cap sized to a slide program (~4–8k tokens). These are starting points, not commitments — Gate 1 exists to tune them.

Reward mapping (Q2 — I draft, Cara checks for hackability)

Turn the metrics into one number per attempt, with execution as a hard gate so broken code earns nothing:

reward = 0  if code fails to execute or yields no valid pptx
reward = wtext·text + wcolor·color + wpos·position + welem·element  otherwise  (weights sum to 1, each term in [0,1])

Anti-hacking notes: give element real weight so the model can't win with an empty slide that trivially matches on color; keep weights blunt (no per-task tuning that invites overfitting). This mirrors powerbench's eventual mapping (per-check booleans → weighted scalar), so whatever we learn about weights and hackability here transfers straight to Phase 2 — that's a deliberate design choice, not a coincidence.

9.  Risks & mitigations

  • SlidesBench repo is unmaintained (no commits since May 2025, 8 open issues incl. a quickstart crash). → We own the fixes; harness already runs in our venv; mint tasks with the repo's own scripts rather than the broken download.
  • Perturbation could break the metrics (degenerate scores). → Pre-check metric stability on a handful of perturbed tasks before building all 50 (§5b).
  • Gated-DeltaNet unsupported in verl. → Gate 1 catches it in 30 minutes; Fireworks fallback ready.
  • Single-turn ≠ powerbench's multi-turn. → Acknowledged scope limit; the multi-turn path is exercised by the powerbench smoke test, not here.
  • Contamination unmeasurable precisely (cutoff unpublished). → The perturbed set sidesteps it entirely; we don't need the cutoff.
